### 另外两台机器按需安装

指导书以 Ubuntu、RISC-V 裸机工具链和 QEMU 4.1.1 为例。Ubuntu/WSL 可先安装构建依赖：

```sh
sudo apt update
sudo apt install build-essential pkg-config libglib2.0-dev libpixman-1-dev zlib1g-dev libfdt-dev python3 wget xz-utils git file
sudo apt install gcc-riscv64-unknown-elf binutils-riscv64-unknown-elf gdb-multiarch
```

下载并编译 QEMU 4.1.1。下列安装路径可以按个人环境调整，但截图和报告必须写出真实路径：

```sh
lab1_qemu_build=$(mktemp -d)
cd "$lab1_qemu_build"
wget https://download.qemu.org/qemu-4.1.1.tar.xz
tar xvJf qemu-4.1.1.tar.xz
cd qemu-4.1.1
./configure --target-list=riscv64-softmmu --prefix="$HOME/.local/opt/qemu-4.1.1" --disable-werror --disable-docs --disable-gtk --disable-sdl --disable-vnc --disable-tools --disable-user
make -j8
make install
cd "$lab1_code_dir"
```

内存较少的电脑把 `-j8` 改为 `-j2`。若 Linux 下载失败，可用 Windows 浏览器下载同一官方地址，再复制到构建目录并从 `tar` 步骤继续；不得以下载失败为由换成未经确认的第三方程序。不同系统若出现编译错误，保留第一条错误并核查依赖，不要强行继续执行安装。QEMU 4.1.1 是指导书示例和课堂建议版本，本组为统一观察选择它，并非指导书绝对禁止所有其他版本。

确认工具版本：

```sh

riscv64-unknown-elf-ld --version
gdb-multiarch --version
make --version
uname -a
cat /etc/os-release
```

预期最后一条显示 `QEMU emulator version 4.1.1`。如果使用课程预编译工具链并包含 `riscv64-unknown-elf-gdb`，可用它替代 `gdb-multiarch`。不要把 QEMU 8.x 的截图标成 4.1.1。

## 2. 构建内核并检查产物

回到最终仓库的 `code/`（同一 Bash 会话可执行 `cd "$lab1_code_dir"`；新终端需填写实际完整路径）：

```sh
make clean
make
ls -lh bin/kernel bin/ucore.img
file bin/kernel bin/ucore.img
riscv64-unknown-elf-readelf -h bin/kernel
riscv64-unknown-elf-readelf -S bin/kernel
riscv64-unknown-elf-nm -n bin/kernel | grep -E 'kern_entry|kern_init|bootstack|bootstacktop|edata|end'
```

检查点：

- `make` 没有编译或链接错误。
- `bin/kernel` 是 ELF64 RISC-V 文件，入口为 `0x80200000`，带调试信息。
- `bin/ucore.img` 是由 `objcopy -O binary` 生成的裸镜像。
- `kern_entry=0x80200000`；本次基线构建中 `bootstack=0x80201000`、`bootstacktop=0x80203000`。

若 WSL 的 `/mnt/...` 目录出现 `Clock skew detected`，先核对 Windows/WSL 时间，等文件时间不再处于未来后重新构建，或在 WSL 的 Linux 文件系统下重新克隆并构建。不能仅凭警告就判定失败，也不能忽略它后只凭产物存在就判定完整成功；仍要检查退出码、重建结果和实际启动/GDB。本机重建虽出现了亚秒级时间戳警告，两个产物哈希与此前相同，随后启动与调试也通过。

**截图 2：** `make` 成功和两个产物；如果一张图放不下，分为 `姓名-02-build.png`、`姓名-03-elf.png`。截图前可执行 `make clean` 保证画面包含真实编译过程。

## 3. 运行原始 `make qemu`

用本人的 QEMU 4.1.1 路径运行原 Makefile：

```sh
make qemu QEMU="$HOME/.local/opt/qemu-4.1.1/bin/qemu-system-riscv64"
```

预期先显示 OpenSBI，随后显示：

```text
(THU.CST) os is loading ...
```

消息后程序停在 `kern_init` 的无限循环，不会自动返回 shell。QEMU 4.1.1 使用 `Ctrl+A`，松开后按 `X` 退出。如果该组合无效，可在另一个终端确认进程归属后结束本人启动的 QEMU。

**截图 3：** 同一画面包含实际命令、`OpenSBI v0.4` 和内核消息，命名 `姓名-04-qemu.png`。不要把使用 `-kernel` 的兼容命令截图写成原始 `make qemu` 结果。

## 4. 两终端启动 GDB

在终端 A 进入 `code/`，用 QEMU 4.1.1 启动调试模式：

```sh
make debug QEMU="$HOME/.local/opt/qemu-4.1.1/bin/qemu-system-riscv64"
```

`-S` 让虚拟 CPU 在第一条指令前暂停，`-s` 让 QEMU 在本机 1234 端口等待 GDB。先退出上一节 QEMU，再启动本节实例。如果端口占用，用 `ss -ltnp 'sport = :1234'` 查看归属，仅退出自己遗留的调试实例，不要终止未知程序。不要给这个无认证的调试端口配置公网转发。

终端 B 进入同一 `code/`，启动 GDB：

本仓库 `make gdb` 目标直接调用 `riscv64-unknown-elf-gdb`；Ubuntu 安装的是 `gdb-multiarch` 时应使用下面的显式命令，不必修改 Makefile。

```sh
gdb-multiarch bin/kernel
```

进入 GDB 后执行：

```gdb
set pagination off
set architecture riscv:rv64
target remote localhost:1234
display/i $pc
p/x $pc
p/x $sp
x/5i $pc
x/8wx 0x1000
x/4wx 0x80200000
```

连接后应有 `pc=0x1000`。进一步运行 `x/16bx 0x80200000`，并在另一个进入同一 `code/` 的 Bash 终端运行 `od -An -tx1 -N16 bin/ucore.img`；逐字节比较应一致。不能仅凭“内存非零”证明装载的是该镜像。相同字节结合 Makefile 的 loader 参数说明 QEMU 在 CPU 运行前已预装镜像。

## 5. 练习 2：逐条跟踪复位代码

在 GDB 中依次执行 `si` 和寄存器检查。不要一次粘贴全部命令，逐步观察每一条指令的影响：

```gdb
si
info registers pc t0 a0 a1
si
info registers pc t0 a0 a1
si
info registers pc t0 a0 a1
si
info registers pc t0 a0 a1
si
info registers pc t0 a0 a1
```

QEMU 4.1.1 的预期过程：

```text
0x1000  auipc t0,0x0       -> t0=0x1000
0x1004  addi a1,t0,32      -> a1=0x1020（DTB 地址）
0x1008  csrr a0,mhartid    -> a0=Hart ID，单核通常为 0
0x100c  ld t0,24(t0)       -> t0=0x80000000（OpenSBI 入口）
0x1010  jr t0              -> pc=0x80000000
```

**截图 4：** 至少包含 `0x1000` 的五条反汇编和逐步执行后的关键寄存器，命名 `姓名-05-reset.png`。

到达 `0x80000000` 后设置内核入口断点：

```gdb
break *0x80200000
continue
p/x $pc
p/x $sp
x/4i $pc
```

预期命中 `kern_entry`，PC 为 `0x80200000`。这一刻 `la sp,bootstacktop` 尚未执行，所以 `sp` 仍是固件阶段的值。

**截图 5：** 包含从 `0x80000000` 继续后命中 `0x80200000`、PC/SP 和入口反汇编，命名 `姓名-06-kernel-entry.png`。

## 6. 检验指导书的 watch 建议

若要验证镜像装载时机，应重新启动 `make debug` 和 GDB，在初始 `pc=0x1000` 时执行：

```gdb
x/4wx 0x80200000
watch *(unsigned int*)0x80200000
break *0x80200000
continue
info breakpoints
```

本工程使用 QEMU `-device loader`。连接 GDB 时内核字节已存在，继续到 `kern_entry` 时写监视点通常不会触发。这个监视点仅观察入口的 4 字节，不代表检查了整个内核区域。请按本人结果记录；不要为了迎合指导书的简化提示而写成“观察到 OpenSBI 写入”。如果实际触发，应保存完整输出并核对 QEMU 版本和启动参数。本节可作为独立补充实验放到第 7 节之后，重启前按下一节的退出步骤结束上一轮调试。

## 7. 练习 1：验证栈和尾调用

在 `0x80200000` 断点处执行：

```gdb
set $firmware_sp = $sp
set $old_ra = $ra
p/x $firmware_sp
p/x $old_ra
p/x &bootstack
p/x &bootstacktop
x/4i $pc
si
si
p/x $pc
p/x $sp
p/x &bootstacktop
si
p/x $pc
p/x $ra
p/x $old_ra
```

`la sp,bootstacktop` 在这次构建中展开为两条机器指令，因此要执行两次 `si` 才完成；此后 `sp` 应等于 `&bootstacktop`。第三次 `si` 执行 `tail kern_init`，PC 应为 `kern_init`，`ra` 应和保存的 `$old_ra` 相同。

**截图 6：** 包含 `bootstack`/`bootstacktop`、执行 `la` 后的 SP，以及执行 `tail` 后的 PC/RA 对照，命名 `姓名-07-stack-tail.png`。

最后输入 `continue`，终端 A 应打印内核消息并进入死循环。完成后在终端 B 按 `Ctrl+C` 中断 GDB，再输入 `detach`、`quit`；在终端 A 按 `Ctrl+A`，松开后按 `X` 退出 QEMU。每次重新验证复位位置都需要重新启动 QEMU，不能只在已运行的会话中重连 GDB。
