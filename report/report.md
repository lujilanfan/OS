## 一、实验目的

1. 在开发机上使用 RISC-V 交叉工具链，把给定最小内核编译、链接为 ELF，并生成供 QEMU 装载的裸镜像。
2. 使用 QEMU 和 GDB 实际观察模拟 CPU 的复位代码、OpenSBI 与内核入口，理解 PC、栈指针和控制权的变化。
3. 区分“QEMU 把镜像放到内存”与“固件把 PC 交给内核”两个动作；理解 ELF 中的入口、段信息与本工程裸镜像的关系。
4. 从源码和实际输出解释 `kern_entry → kern_init → cprintf → SBI` 的最短运行路径，形成可复核的实验记录。

本次课堂明确称 Lab1 为无新增编程任务的演示实验。`malloc`、进程管理等不是本次已有源码体现的完成项；若正式 Lab1 练习另有要求，应补充而非凭课堂摘要推断没有。

## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

开发机上的交叉编译器产生 RISC-V 指令；链接脚本把入口和内核代码定位到 `0x80200000`。QEMU `virt` 机器启动时，GDB 看到 PC 初始为 `0x1000`，执行复位代码后到 `0x80000000` 的固件，固件完成初始化并把控制权交给 `0x80200000` 的 `kern_entry`。内核入口设置栈，再进入 `kern_init`；后者输出启动消息并停在无限循环。

这里有两条不同的路径：`bin/kernel` 是带 ELF 头、符号和调试信息的文件，用于链接信息与 GDB；`bin/ucore.img` 是通过 `objcopy -O binary` 生成的裸镜像。本工程 Makefile 的 QEMU `-device loader,file=...,addr=0x80200000` 参数把裸镜像写入指定地址，**并不意味着 OpenSBI 在本实验从磁盘读取它**。在本机 QEMU 8.2.2 上，该 loader 参数单独使用时不会替固件设置下一阶段 PC，所以“镜像存在于内存”和“成功启动内核”不能混为一谈。QEMU 的通用 loader 文档亦明确不指定 `cpu-num` 时不设置 CPU PC：<https://www.qemu.org/docs/master/system/generic-loader.html>。

### 3.2 各阶段如何衔接

1. `Makefile` 通过 `riscv64-unknown-elf-*` 编译/链接；`tools/kernel.ld` 设置 `BASE_ADDRESS = 0x80200000` 和 `ENTRY(kern_entry)`。
2. 链接产生 ELF `bin/kernel`；`objcopy` 删除 ELF 容器得到 `bin/ucore.img`。QEMU 装载镜像和固件交权是两件事。QEMU `virt` 文档说明标准 `-kernel` 路径配合默认 OpenSBI 固件：<https://www.qemu.org/docs/master/system/riscv/virt.html>。
3. 实测 GDB 停在 `0x1000 → 0x80000000 → 0x80200000 → 0x8020000a`。前两处属于复位/固件阶段，后两处分别为 `kern_entry`、`kern_init`。
4. `kern/init/entry.S` 的 `la sp, bootstacktop` 初始化栈，`tail kern_init` 转入 C；`kern/init/init.c` 调用 `memset`、`cprintf`，随后无限循环。
5. 输出由格式化函数进入控制台/SBI 调用，固件负责将字符送到 QEMU 终端。代码没有进入用户态，也未实现进程调度或动态内存分配。

## 四、实验内容与实现

### 练习 1：工具链、构建与产物

在 `code/` 目录执行 `make`，实际退出码为 0，产生 `bin/kernel`、`bin/ucore.img`。`file` 和 `readelf -h` 证实前者是带调试信息的 ELF64 RISC-V 可执行文件、入口 `0x80200000`；后者显示为普通 `data`，不能拿来当作含 ELF 头的程序给 `readelf` 解释。实测大小分别为 43,496 B、12,296 B。两文件的 SHA-256 分别为：

```text

bin/ucore.img  36bef3842e20e33667dd8075563b890317fb18f9654ca961dcef4dc145eab84c
```

本机源文件在 Windows 盘通过 WSL 的 `/mnt/e/` 访问，构建时 Make 曾提示轻微 `Clock skew detected`（文件时间相差约 0.56 秒），但命令退出码为 0，产物经格式/运行检查。复验者应记录自己的完整构建输出，而不是复制这台电脑的哈希或截图。

### 练习 2：ELF、装载位置和启动入口

**负责人（待确认）：** 2410718-姚均，2412932-李潇健交叉核对。

`readelf -h -l -S bin/kernel` 给出 ELF 入口 `0x80200000`；实际 `.text` 位于 `0x80200000`，`.rodata` 位于 `0x802004c0`，`.data` 位于 `0x80201000`，`.sdata` 位于 `0x80203000`。`nm -n` 显示 `kern_entry=0x80200000`、`kern_init=0x8020000a`、`bootstack=0x80201000`、`bootstacktop=0x80203000`、`edata=end=0x80203008`。链接脚本虽然定义 `.bss` 输出节，本次生成的 ELF 节表未出现实际 `.bss` 节；因此本次 `memset(edata, 0, end-edata)` 的长度为 0，不能写作“实测清零了一段非空 BSS”。

本机对原 Makefile 的 `-device loader,file=bin/ucore.img,addr=0x80200000` 单独启动方式做了额外调试：GDB 在 `0x80200000` 读到与 `kern_entry` 一致的指令字节，证明镜像已装入内存；继续运行后 OpenSBI 输出 `Domain0 Next Address : 0x0000000000000000`，没有出现内核消息。在同一 QEMU 8.2.2 上，改用 `-kernel bin/ucore.img` 后 OpenSBI 显示 `Domain0 Next Address : 0x0000000080200000`，并打印 `(THU.CST) os is loading ...`。这是一项**版本/启动参数差异**，不应把原始 `make qemu` 写成“成功看到内核输出”。若课程固定 QEMU 4.1.1，应在指定版本再复验原命令。

### 练习 3：GDB 追踪复位到内核

**负责人（待确认）：** 2412932-李潇健；另两位需独立复现基本断点。

本机以 `qemu-system-riscv64 -machine virt -nographic -bios default -kernel bin/ucore.img -s -S` 启动调试；另一个终端用 `gdb-multiarch bin/kernel`，设置 `set architecture riscv:rv64`、`target remote localhost:1234`。实际观察如下：

| 停止点/动作 | 实测 PC | 实测 SP | 解释 |
|---|---|---|---|
| 连接后 | `0x1000` | `0x0` | QEMU `virt` 复位入口，尚未执行内核 |
| 一次 `si` | `0x1004` | 未记录 | 复位代码向下一条指令前进 |
| `break *0x80000000` | `0x80000000` | `0x0` | 进入固件区 |
| `break *0x80200000` | `0x80200000` | `0x80046eb0` | 命中 `kern_entry`，**此刻尚未执行**设置内核栈的指令 |
| `break kern_init` | `0x8020000a` | `0x80203000` | 入口已把 SP 设置为 `bootstacktop`，进入 C 函数 |

`0x80200000` 的反汇编可见 `auipc sp,0x3`，`0x80200004` 为 `mv sp,sp`，`0x80200008` 跳到 `0x8020000a`。这些是本次编译/链接与反汇编的具体结果，不能把优化后的机器指令和源文件中的伪指令逐字等同。GDB 观察的是 QEMU 模拟的**来宾 CPU**；本次并未使用宿主 GDB 单步 QEMU 本身的 C 源码，不能声称追到了 QEMU loader 的内部实现。

### 练习 4：最小内核输出与结束状态

**负责人（待确认）：** 2410764-朱彦泽；本人源码核对和复现待补。

源码调用链为 `kern_init → cprintf → vcprintf/vprintfmt → cons_putc → sbi_console_putchar → sbi_call → ecall`，其中部分小函数在 `-O2` 下可能内联，不能要求每一层都有可断的独立符号。`kern_init` 的消息常量带一个换行，而 `cprintf("%s\n\n", message)` 又添加两个换行；本机最终看到 `(THU.CST) os is loading ...`。其后是 `while (1)`，所以 QEMU 持续运行、外部超时结束是预期行为，不是“内核正常退出”。

## 六、实验总结与收获

### 对操作系统的理解

本次观察到的最关键界限是复位代码、固件和内核各自负责不同阶段：PC 进入内核之前，不能把看到的代码都叫“操作系统内核”。另一条界限是装载与执行：QEMU loader 可把裸镜像写进内存，但不保证固件下一阶段入口正确；本机的两组 QEMU 参数恰好把这种区别显露出来。ELF 入口和段/节信息服务于链接、装载与调试，而裸镜像只是字节序列；理解两者差异可用于定位“文件编好了却没启动”的问题。栈指针在 `kern_entry` 前后改变，说明 C 代码运行前必须先建立最基本的执行环境。

本次尚未观察或实现进程调度、系统调用、虚拟内存页表、用户态程序及动态内存分配。课堂用这些主题解释课程方向，但不能把它们写成 Lab1 已验证功能。三位成员需补上各自“我原来误解了什么、哪条证据改变了看法”的真实总结。

### AI 协作开发的经验

本次 AI 主要帮助把课堂口述转为可核验的命令、证据与报告结构；关键结论由编译结果、GDB 寄存器和源码反查，而非直接照抄生成文本。例如初步规划容易把 `-device loader` 与“内核已启动”连在一起，但本机检查到前者已把指令放入 `0x80200000`，OpenSBI 下一阶段地址仍为 0；再用 `-kernel` 做区分性测试才确认问题在交权方式。这个修正过程应在正式提交时配上原始对话、命令和结果。另两位成员的 AI 使用情况和体会待本人填写；未使用就如实写未使用。
