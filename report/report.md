## 一、实验目的

依据指导书第 53 页，本实验围绕最小可执行内核和启动流程展开，目标包括：

1. 理解链接脚本如何规定内核的内存布局、入口符号和 `0x80200000` 加载地址。
2. 使用 RISC-V 交叉编译工具链生成 ELF 内核，再用 `objcopy` 得到裸二进制镜像。
3. 理解 QEMU、复位代码、OpenSBI 和内核之间的启动交接关系。
4. 理解内核入口如何建立栈并转入 C 函数，以及如何通过 SBI 的 `ecall` 服务完成格式化输出。
5. 掌握 QEMU 远程调试接口和 GDB 的断点、单指令执行、寄存器与内存检查方法，用实际观察验证启动流程。

Lab1 是后续实验的准备。本次给定内核能够格式化输出后进入死循环，不包含 `malloc`、进程管理、调度、页表或用户态程序等实现任务。

## 三、实验整体逻辑分析

### 3.1 逻辑主线

本章按“构建内核 → 布置镜像 → 固件交权 → 建立 C 运行环境 → 通过 SBI 输出 → 用 GDB 验证”的顺序展开：

```text
C/汇编源码
  ↓ RISC-V 交叉编译、链接脚本
bin/kernel（ELF：入口、段、符号、调试信息）
  ↓ objcopy -O binary
bin/ucore.img（裸二进制）
  ↓ QEMU loader 在 CPU 开始前放入 0x80200000
PC=0x1000 的复位代码 → PC=0x80000000 的 OpenSBI
  ↓ OpenSBI 初始化并把控制权交给 S 模式内核
PC=0x80200000 的 kern_entry
  ↓ 建立内核栈、尾调用 kern_init
cprintf → 格式化输出 → cons_putc → SBI ecall → QEMU 终端
  ↓
while (1)
```

这些阶段存在依赖关系：如果 ELF 入口和装载地址不一致，CPU 不能从正确机器码开始；如果入口未设置栈，C 函数无法安全执行；如果 SBI 输出封装不正确，内核即使运行也无法给出可见反馈；GDB 则负责把每个阶段从“预期”变成可观察的证据。

### 3.2 谁负责装载内核

指导书第 54、58—63 页有“OpenSBI 加载内核”的概括性表述，但第 64 页明确说明“现有 ucore 中，操作系统的加载实际上由 QEMU 完成”。课堂记录也指出 Makefile 使用：

```text
-device loader,file=bin/ucore.img,addr=0x80200000
```

QEMU 在虚拟 CPU 执行第一条指令之前，就把裸镜像写入 `0x80200000`。本机在 PC 仍为 `0x1000` 时检查该内存，已经与 `bin/ucore.img` 开头字节一致；此后设置的 `watch *0x80200000` 没有捕获写入。由此，本实验的准确表述是：**QEMU 负责预装载镜像，OpenSBI 负责硬件/运行环境初始化及最终控制权移交。** 真实硬件或其他启动方案可以由 bootloader 读取存储设备并装载内核，但那不是本工程当前 Makefile 的实现。

## 四、实验内容与实现

### 练习 1：理解内核启动中的程序入口操作

**负责人：** 2412932-李潇健

指导书问题：`la sp, bootstacktop` 完成什么操作、目的是什么？`tail kern_init` 完成什么操作、目的是什么？

#### `la sp, bootstacktop`

`la` 是加载地址的伪指令。它把链接符号 `bootstacktop` 的地址写入栈指针寄存器 `sp`。`entry.S` 先在 `.data` 中按页对齐定义 `bootstack`，再用 `.space KSTACKSIZE` 预留栈空间；`bootstacktop` 位于这块空间的高地址端。栈按 RISC-V 约定由高地址向低地址增长，所以空栈的初始 `sp` 应设置为 `bootstacktop`。

本次构建的符号值为：

```text
bootstack    = 0x80201000
bootstacktop = 0x80203000
KSTACKSIZE   = 0x2000 = 8192 bytes
```

GDB 在 `kern_entry` 第一条指令执行前观察到 `sp=0x8001bd80`，这是 QEMU 4.1.1/OpenSBI 阶段使用的栈。对 `la` 展开的两条机器指令单步执行后，`sp=0x80203000`，与 `&bootstacktop` 相等。此操作为随后执行的 C 函数建立内核自己的 8 KiB 栈，满足函数调用、局部变量和保存寄存器的基本要求。

本次反汇编中，`la` 展开为：

```asm
0x80200000 <kern_entry>:   auipc sp,0x3
0x80200004 <kern_entry+4>: mv    sp,sp
```

第二条看似没有变化，是因为链接完成后当前 PC 加上偏移已恰好得到 `0x80203000`；`la` 的具体展开会随链接地址和重定位结果变化，理解时应以“把符号地址放入 `sp`”为准。

#### `tail kern_init`

`tail` 是尾调用伪指令。它无条件跳转到 `kern_init`，不写入返回地址寄存器 `ra`。本次反汇编为：

```asm
0x80200008 <kern_entry+8>: j 0x8020000a <kern_init>
```

单步执行后，PC 从 `0x80200008` 到 `0x8020000a`，`ra` 仍为进入 `kern_entry` 前 OpenSBI 留下的 `0x80000a02`。这样不会额外建立一层永远无法返回的调用栈帧。`kern_init` 被声明为 `noreturn`，最后进入 `while (1)`，因此入口代码只需要把控制权永久移交给它。

**练习 1 结论：** `la sp, bootstacktop` 建立内核 C 代码使用的栈；`tail kern_init` 在不设置新返回地址的情况下进入 C 内核入口。两者共同完成从固件环境到最小内核运行环境的交接。

### 练习 2：使用 GDB 验证启动流程

**负责人：** 2410718-姚均

指导书要求从加电开始跟踪到内核第一条指令，并回答最初指令位于哪里、主要完成什么功能。本次主要证据使用 QEMU 4.1.1，与指导书示例版本一致。

#### 调试过程

1. 李潇健在本机终端 A 运行 `make debug QEMU=/home/lxj/.local/opt/qemu-4.1.1/bin/qemu-system-riscv64`，QEMU 以 `-S -s` 启动，CPU 暂停在复位位置并监听 1234 端口。
2. 终端 B 运行 `gdb-multiarch bin/kernel`，设置 `riscv:rv64` 架构并连接 `localhost:1234`。
3. 初始 `pc=0x1000`。使用 `x/5i $pc`、`si` 和 `info registers` 逐条观察复位代码。
4. CPU 执行跳转后到达 `0x80000000` 的 OpenSBI。设置 `break *0x80200000` 并继续，最终命中 `kern_entry`。
5. 在 `kern_entry` 单步验证 `sp` 被改为 `bootstacktop`，再验证 `tail` 跳入 `kern_init` 且 `ra` 不变。

#### 上电后最初几条指令及功能

QEMU 4.1.1 的首批有效指令位于 MROM 的 `0x1000`—`0x1010`：

| 地址 | 指令 | 实测寄存器变化 | 主要功能 |
|---|---|---|---|
| `0x1000` | `auipc t0,0x0` | `t0=0x1000` | 取得复位代码的 PC 相对基址 |
| `0x1004` | `addi a1,t0,32` | `a1=0x1020` | 把设备树 DTB 地址作为第二个启动参数 |
| `0x1008` | `csrr a0,mhartid` | `a0=0` | 读取当前硬件线程 Hart ID，作为第一个启动参数 |
| `0x100c` | `ld t0,24(t0)` | `t0=0x80000000` | 从复位向量常量区取出 OpenSBI 入口地址 |
| `0x1010` | `jr t0` | `pc=0x80000000` | 跳转到 OpenSBI，开始固件初始化 |

因此，最初几条指令并不负责完整初始化，也不在这里读取磁盘。它们准备 OpenSBI 所需的 Hart ID 和设备树地址，从复位向量中取得固件入口，然后跳转到 `0x80000000`。OpenSBI 运行后完成固件初始化并最终跳转到 `0x80200000` 的内核入口。

QEMU 8.2.2 的复位代码比 4.1.1 多传递了一个参数：在 `a2` 中放入下一阶段入口相关信息的地址，所以地址和寄存器序列略有差异。这也说明指令序列依赖 QEMU 版本；报告以指导书示例 4.1.1 为主，不能混用不同版本的截图和寄存器值。

#### `watch *0x80200000` 的实测解释

在 PC 仍为 `0x1000` 时，`0x80200000` 已经包含 `kern_entry` 的机器码。此时设置 `watch *(unsigned int*)0x80200000` 并继续，直到命中内核入口，监视点没有触发。该监视点只覆盖入口的 4 字节，不能据此断言整个内核范围都没有写入；预装载结论来自复位时内存与镜像开头一致、Makefile 参数及指导书第 64 页的共同印证。指导书建议的监视点可用于检查被监视位置的运行期写入，但无法捕获 GDB 连接前发生的 QEMU 预装载“瞬间”。

**练习 2 结论：** 实测控制流为 `0x1000（MROM）→ 0x80000000（OpenSBI）→ 0x80200000（kern_entry）→ 0x8020000a（kern_init）`。启动过程完成了启动参数准备、固件初始化、控制权交接、栈初始化和最小内核输出。

### 核心功能模块理解

指导书第 89—90 页要求解释每个功能的核心函数或模块。本实验相关模块如下：

| 模块/文件 | 核心作用 | 与其他模块的关系 |
|---|---|---|
| `tools/kernel.ld` | 指定 RISC-V 架构、`kern_entry` 入口、`0x80200000` 基址和各 section 布局 | 链接结果必须和 QEMU 装载地址、入口汇编一致 |
| `kern/init/entry.S` | 定义 `kern_entry`，预留内核栈，初始化 `sp`，尾调用 `kern_init` | 承接 OpenSBI，建立 C 代码运行所需的最小环境 |
| `kern/init/init.c` | 清理 `edata` 到 `end`，调用 `cprintf`，然后死循环 | 是最小内核的 C 入口和可见启动标志 |
| `libs/sbi.c` | 按 SBI legacy 调用约定把服务号放入 `a7/x17`、参数放入 `a0`—`a2`，执行 `ecall` | 将 S 模式内核请求转交 M 模式 OpenSBI |
| `kern/driver/console.c` | 用 `cons_putc` 封装 SBI 单字符输出 | 连接高层格式化输出和底层 SBI |
| `kern/libs/stdio.c`、`libs/printfmt.c` | 完成 `cprintf`、格式解析和逐字符回调 | 不依赖宿主机 glibc，为内核提供自己的格式化输出 |
| `Makefile`、`tools/function.mk` | 组织编译、链接、`objcopy`、QEMU 启动和 GDB 入口 | 把源码转换为可运行、可调试的实验对象 |

本次构建中 `edata=end=0x80203008`，没有实际占空间的 `.bss`，所以 `memset(edata,0,end-edata)` 长度为 0。源码体现了通用的 BSS 清零流程，但本次二进制不能作为“确实清零了非空 BSS”的证据。

`ucore.img` 不保留 ELF 文件头、节表或调试符号，不能把它解释成“原 ELF 文件去掉符号后原样加载”。一般 `.bss` 为不占 ELF 文件数据空间的 `NOBITS` 节，裸镜像是否包含某段填充还取决于实际节布局，不能笼统声称 `.bss` 总会让 BIN 膨胀。链接脚本中的 `ALIGN(0x1000)` 表示按 4096 字节对齐，而不是按“2 的 0x1000 次方”对齐。

## 六、实验总结与收获

### 对操作系统的理解

1. **启动是分阶段交权。** 复位代码只准备启动参数并跳到固件；OpenSBI 在 M 模式初始化平台并把控制权交给 S 模式内核；`kern_entry` 再建立内核自己的栈。固件代码和内核代码位于不同地址、承担不同职责。
2. **文件装载和 CPU 跳转是两个动作。** QEMU loader 把裸镜像放进物理内存，OpenSBI 最终修改控制流进入镜像。内存中已经有代码，不代表 PC 一定会到达该代码。
3. **ELF 与裸镜像用途不同。** ELF 保存入口、section、符号和调试信息，适合链接分析与 GDB；`ucore.img` 是线性字节镜像，适合按固定地址装入内存。二者来自同一程序但不能混作同一种文件。
4. **C 代码依赖最低运行环境。** 在进入 `kern_init` 前必须建立有效栈；内核不能依赖另一个操作系统的 libc，而是通过自己的格式化代码和 SBI 服务完成输出。
5. **实验与 OS 原理的联系。** 本实验实际体现引导、特权级、ABI、内存布局和固件接口；其中 SBI `ecall` 与后来用户态系统调用都属于受控的特权级转换，但调用方向和服务对象不同。

OS 原理中很重要但本实验尚未对应的内容包括：中断与异常处理、物理内存分配、页表和虚拟内存、进程/线程及上下文切换、调度、同步互斥、系统调用、文件系统和设备驱动。它们会在后续 Lab 中逐步加入，不能写成 Lab1 已实现功能。

### AI 协作开发的经验

这次 AI 的有效作用不是生成内核代码，而是把指导书问题拆成可验证的观察点。例如，“OpenSBI 加载内核”若只照抄概括性文字，会和当前 Makefile 的 QEMU loader 冲突；通过在 CPU 尚未运行时检查 `0x80200000`、设置写监视点并比较课堂讲解，才确定本工程是 QEMU 预装载、OpenSBI 交权。另一个例子是 QEMU 8.2.2 与 4.1.1 的 loader 行为不同，最终根据指导书版本重新编译 4.1.1 并复现原命令。由此可见，AI 给出的分析需要经过源码、版本和调试结果三方面核对。
