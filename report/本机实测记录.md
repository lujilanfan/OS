# 本机实测记录（文字证据，不替代终端截图）

日期：2026-10-02。实验目录为候选包的 `code/`，开发环境为 Windows 上的 WSL Ubuntu 24.04。此文件保留可以复核的关键命令和输出摘录；QEMU 在输出后持续运行是 `kern_init` 无限循环所致。该记录不代表姚均、朱彦泽两台电脑的结果。

## 工具及构建

```text
riscv64-unknown-elf-gcc --version  -> 13.2.0
riscv64-unknown-elf-ld --version   -> GNU ld 2.42
qemu-system-riscv64 --version      -> 8.2.2
gdb-multiarch --version            -> 15.1
make --version                     -> 4.3
make                               -> 退出码 0，产生 bin/kernel 与 bin/ucore.img
file bin/kernel                    -> ELF 64-bit LSB executable, UCB RISC-V, with debug_info
file bin/ucore.img                 -> data
```

`readelf -h bin/kernel` 摘录：`Class: ELF64`；`Machine: RISC-V`；`Entry point address: 0x80200000`。`readelf -S` 的实际节地址为 `.text=0x80200000`、`.rodata=0x802004c0`、`.data=0x80201000`（大小 `0x2000`）、`.sdata=0x80203000`（大小 8）；节表里没有 `.bss`。`nm -n` 摘录：

```text
0000000080200000 T kern_entry
000000008020000a T kern_init
0000000080201000 D bootstack
0000000080203000 D bootstacktop
0000000080203008 D edata
0000000080203008 D end
```

`bootstacktop - bootstack = 0x2000 = 8192` 字节；`end - edata = 0`。`bin/kernel` 为 43,496 B；`bin/ucore.img` 为 12,296 B。哈希见 `report.md` 第四节，用于识别本机这次构建，不是三台机器必须相同的评分条件。

## QEMU 两种参数的区分性测试

在 `code/` 执行原 Makefile 的 `make qemu`，QEMU 8.2.2 的 OpenSBI v1.3 显示：

```text
Firmware Base             : 0x80000000
Domain0 Next Address      : 0x0000000000000000
Domain0 Next Mode         : S-mode
```

等待约 5 秒没有出现内核消息，然后用 `timeout` 发送 SIGTERM 停止；因此这个命令在本机**不能**作为“内核启动成功”的截图来源。另以 GDB 连接 `-device loader,file=bin/ucore.img,addr=0x80200000 -s -S` 运行，可在 `0x80200000` 读到 `kern_entry` 对应的指令，说明裸镜像确实进入指定内存地址，失败环节在后续控制权移交，而非“没有加载文件”。

执行：

```sh
qemu-system-riscv64 -machine virt -nographic -bios default -kernel bin/ucore.img
```

同一台机器的输出关键行变为：

```text
Domain0 Next Address      : 0x0000000080200000
Domain0 Next Mode         : S-mode
(THU.CST) os is loading ...
```

消息打印后内核处于源码里的无限循环，外部 `timeout` 发 SIGTERM 才结束；因此其进程退出码不能被当作内核功能测试结果。

## GDB 观察

在 QEMU `-kernel bin/ucore.img -s -S` 模式下连接 `gdb-multiarch bin/kernel`，`target remote localhost:1234` 后：

```text
连接时                pc=0x1000        sp=0x0
si 一次               pc=0x1004
break *0x80000000     pc=0x80000000    sp=0x0
break *0x80200000     pc=0x80200000    sp=0x80046eb0
break kern_init       pc=0x8020000a    sp=0x80203000
```

在 `0x80200000` 断下时尚未执行 `la sp, bootstacktop`，所以此刻不是 `0x80203000`；到 `kern_init` 才能观察到该栈顶。GDB 指令级跟踪的是 QEMU 模拟的来宾 RISC-V CPU，不是单步调试 QEMU 本体的实现源码。
