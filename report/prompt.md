## 实际分析—测试—修正链

1. 从课堂叙述和原 Makefile 得到待验证的启动路径：QEMU loader 把镜像置于 `0x80200000`，固件最终应交给内核。
2. 用原 `make qemu` 对照：本机 QEMU 8.2.2 显示 OpenSBI 下一阶段地址为 0，没有内核消息。GDB 又看到 `0x80200000` 的指令确已在内存，故“装载成功”并不推出“已转入内核”。
3. 换用 `-kernel bin/ucore.img` 验证：下一阶段地址变为 `0x80200000`，GDB 命中内核入口，终端打印消息。报告因此把两种启动参数及其限制分别陈述。
4. 用 `readelf`/`nm` 修正另一种容易照抄源码得出的结论：虽然 `kern_init` 写了 `memset(edata,0,end-edata)`，本次二者地址相同、长度为 0，不能声称真的清空了非空 BSS。
5. 加入 2026 指导书后确认正式要求只有两道练习：解释入口的 `la`/`tail`，以及从 `0x1000` 跟踪到 `0x80200000` 并回答首批指令的功能。报告据此重新组织。
6. 按指导书示例编译 QEMU 4.1.1。原始 `make qemu` 在该版本打印内核消息，说明此前 QEMU 8.2.2 的失败是版本/启动接口差异，不能据此判定课程代码错误。
7. 在 QEMU 4.1.1 下逐条验证 `0x1000` 的五条复位指令、`sp=bootstacktop` 和 `tail` 不改变 `ra`。同时确认连接 GDB 时镜像已在 `0x80200000`，写监视点不会捕获 CPU 启动前的 QEMU 预装载。
